# 학습 데이터 구성 검토

검토 기준일 2026-10-02 · 대상 브랜치 `claude/elegant-hamilton-z3exv3` · 시험 10/25 (D-23)

## 1. 한 줄 결론

> **지금 규모에서 서버 DB 는 필요 없다. localStorage 를 유지하되, "저장 계층의 약속"(버전 · 마이그레이션 · 검증된 백업)을 먼저 세우고, 시도 이력이 필요해질 때 같은 논리 모델 위에서 IndexedDB 로 옮긴다.**

| 계층 | 내용 |
|---|---|
| 상위 원리 | 저장소는 바꿔도 **논리 모델(항목 · 시도 · 북마크 · 완료)** 은 바뀌지 않게 한다 |
| 하위 전략 | ① 저장 계층을 한 곳에 모은다 ② 스키마 버전과 마이그레이션을 둔다 ③ 백업은 검증 후 복원한다 ④ 콘텐츠는 빌드 때 검증한다 |
| 실행 포인트 | §6 의 P0 → P3 단계 (P0 는 반나절, 지금 해도 안전) |

## 3. 발견 사항

심각도: **H** = 데이터 손실·오동작 가능 · **M** = 기능 확장을 막음 · **L** = 위생

| # | 심각도 | 발견 | 근거 | 영향 |
|---|---|---|---|---|
| 1 | **H** | **백업 가져오기에 검증이 없고, 용량 초과가 "유효하지 않은 백업 파일"로 보인다** | `DashboardPage.jsx` 의 가져오기: `jungchogi_` 로 시작하는 모든 키를 `localStorage.setItem` 으로 그대로 쓰고, 같은 `try` 안에서 예외를 삼킨다 | 손상·수기 편집된 값이 그대로 들어가 화면이 깨질 수 있고, 중간에 실패하면 **일부만 복원**된다. 오류 메시지가 원인을 가린다 |
| 2 | **H** | **스키마 버전과 마이그레이션 체계가 없다** | 마이그레이션이 즉석 코드로 두 번 있다(`flashcard_known` 이름 변경, `lesson_bookmarks` → `bookmarks`) | 형식을 바꿀 때마다 즉석으로 처리해야 하고, 백업 파일이 어느 버전인지 알 수 없다 |
| 3 | M | **시도(attempt) 이력이 없다 — 마지막 상태만 있다** | `quiz_results` · `exam_results` · `flashcard_known` 이 같은 "문항 상태"를 키·모양만 달리해 세 곳에 저장. 시각·횟수 없음 | 정답률 추이, "마지막으로 맞힌 지 N일", 약점 영역 분석, 오답 외 문항의 간격 반복이 불가능하다 |
| 4 | M | **완료 체계가 둘이다** | `day_checks`(Day 문서 1~14, 시험일까지 균등 분배) vs `roadmap_checks`(D-n 로드맵) | 같은 날 해야 할 일이 두 곳에서 달라 보인다. 통합 결정이 보류 중이다 |
| 5 | M | **콘텐츠 읽기가 정규식에 의존하고, 이름과 카드 수가 어긋난다** | "암기 119선" 덱은 파서가 `보강 N` 섹션 단위로 **24카드**만 만든다. 제목 형식이 바뀌면 문항이 **조용히** 사라지는 구조 | 119개 항목을 24카드 단위로만 외움 표시·북마크할 수 있고, 파서 회귀를 CI 가 잡으려면 실제 자료 기준 검증이 따로 필요하다 |
| 6 | M | **오답노트가 문제 본문을 복사해 저장한다** | `addWrongNote` 가 title · context · code · answer · pitfall 을 통째로 저장 | 원본 md 를 고쳐도 오답노트에는 반영되지 않는다 (용량 문제는 아님) |
| 7 | L | 학습 노트 섹션 id 가 위치 기반(`파일번호-순번`) | `parseStudyNotes` | 북마크를 **문서 단위**로 한정한 이유. 섹션 단위 북마크는 문서가 바뀌면 어긋난다 |
| 8 | L | 접두사 없는 키와 미사용 키 | `jungchogi-theme` 는 백업·초기화 대상에서 빠진다. `exam_type` 등 더 이상 읽지 않는 키가 기존 사용자 브라우저에 남을 수 있다 | 백업으로 테마가 복원되지 않음, 잔존 데이터 |
| 9 | L | 단일 기기·단일 브라우저 | 동기화 없음 | 브라우저 데이터를 지우면 사라진다. 지금의 안전망은 수동 내보내기뿐이다 |

## 4. DB 가 필요한가 — 선택지 비교

| | A. localStorage 유지 + 계층 정비 | B. IndexedDB | C. 서버 DB (예: Postgres/Supabase) + 로그인 |
|---|---|---|---|
| 해결하는 것 | 1·2·8 | 3 (이력이 수천 건 이상일 때) | 9 (기기 간 동기화) |
| 비용 | 낮음 (반나절 ~ 1일) | 중간 (비동기 API 로 전환, 테스트 재작성) | 높음 (인증 · 개인정보 · 보안 · 운영, 정적 SPA 구조 변경) |
| 위험 | 낮음 | 중간 (동기 읽기 가정이 깨짐) | 높음 |
| 오프라인 | 됨 | 됨 | 별도 구현 필요 |
| 지금 필요성 | **있음** | 시도 이력을 도입할 때 | **없음** (사용자가 기기 간 동기화를 요구하기 전까지) |

**권고: A 를 지금, B 는 시도 이력(P2) 이후 데이터가 커질 때, C 는 동기화가 실제 요구가 될 때.**
시험이 3주 남은 지금은 저장소 교체보다 **복원 안전성(발견 1·2)** 과 **콘텐츠 검증(발견 5)** 이 효과가 크다.

## 5. 목표 논리 모델 (저장소와 무관)

어느 저장소를 쓰더라도 이 모양을 유지하면 이전 비용이 작다.

| 엔티티 | 필드 | 성격 | 현재 대응 |
|---|---|---|---|
| **Item** | `ref = 종류:id`, 제목, 분류 | 읽기 전용 콘텐츠 | md · `lessons.js` (저장 안 함) |
| **Attempt** | `ref`, `at`, `result(correct/incorrect/answered)`, `context(quiz/exam/flashcard/lesson)` | 추가만 하는 이력 | **없음** (`quiz_results` · `exam_results` · `flashcard_known` 가 마지막 상태만 보관) |
| **Bookmark** | `ref`, `at` | 상태 | `bookmarks` ✅ (이번 변경) |
| **Completion** | `scope(day / roadmap)`, `key` | 상태 | `day_checks` · `roadmap_checks` |
| **ReviewState** | `ref`, `reviewCount`, `lastReviewed`, `mastered` | 상태 | `wrong_notes` 의 일부 |
| **StudyTime** | `date`, `minutes` | 집계 | `study_time` |
| **Settings** | `examDate`, `theme` | 설정 | `exam_date` · `jungchogi-theme` |

핵심 규칙은 **`ref` 를 항상 `종류:id` 로 쓴다**는 것이다. 북마크는 이미 이 규칙을 따르고(`quiz100:001`, `codeDrill:C-01`, `doc:<파일 이름>`), 오답노트의 `source + id` 도 같은 뜻이라 나중에 `ref` 로 합치기 쉽다. 오답노트는 Attempt 와 ReviewState 에서 **파생**되는 뷰로 바꿀 수 있다.

## 6. 실행 계획

| 단계 | 내용 | 규모 | 위험 | 비고 |
|---|---|---|---|---|
| **P0** | ① 백업 가져오기: 형식 검증 → 전부 쓰기 전에 검사 → 실패 시 롤백, 용량 초과는 별도 메시지 ② 내보내기를 `{ schema, exportedAt, data }` 로 버전화(옛 형식도 읽기) ③ `schema_version` 키와 **순서 있는 마이그레이션 목록**으로 즉석 마이그레이션 대체 ④ 테마 키를 백업에 포함하거나 제외한다고 명시 ⑤ 미사용 키(`exam_type` 등) 정리 | 반나절 | 낮음 | 발견 1·2·8 |
| **P1** | 콘텐츠를 빌드 때 JSON 으로 변환하고 CI 에서 **id 유일성 · 개수 · 제목 형식**을 검사. 암기 119선의 카드 단위(24카드 vs 119항목)를 정하고 이름을 바로잡거나 항목 단위로 쪼갠다 | 1일 | 중간 | 발견 5. 검색 색인도 미리 만들 수 있다 |
| **P2** | `Attempt` 로그 도입(상한 N건의 고리 버퍼). `quiz_results` · `exam_results` · `flashcard_known` 은 읽기 호환 유지. 이후 정답률·약점·간격 반복을 이력 기반으로 | 1~2일 | 중간 | 발견 3·6 |
| **P3** | 이력이 커지면 IndexedDB, 기기 간 동기화가 요구되면 서버 DB | 큼 | 높음 | 발견 9. 요구가 생기기 전에는 하지 않는다 |

의존 관계: P0 → (P1, P2 병행 가능) → P3. **P0 만 해도 가장 큰 위험(발견 1·2)이 사라진다.**

## 7. 이번 변경(북마크)이 이 모델에 맞춘 것

- 저장: `bookmarks` 키 하나에 `{ "<종류>:<id>": 북마크한 시각 }`. 종류는 `lesson` · `quiz100` · `bogang` · `codeDrill` · `doc` (`src/domain/bookmarks.js`).
- 식별자는 각 자료가 이미 쓰는 안정적인 id(교재 번호, 레슨 id, 문서 **파일 이름**)를 쓴다. 문서 목록의 순서가 바뀌어도 가리키는 문서는 같다.
- 처음 만든 `lesson_bookmarks` 는 불러올 때 한 번 `lesson:<id>` 로 합치고 지운다. 저장이 실패하면 옛 키를 남겨 다음에 다시 시도한다(`migrateLegacyBookmarks`).
- 북마크 화면은 id 만 저장하고 **제목은 원본 md 에서 읽는다**. 원문이 바뀌어도 어긋나지 않고, 사라진 자료는 "자료를 찾을 수 없습니다"로 표시한다.
- 학습 노트 섹션은 위치 기반 id 라 문서 단위로만 북마크한다(발견 7).

## 8. 결정이 필요한 질문

1. **암기 119선**을 지금처럼 24카드(섹션 단위)로 둘까, 119개 항목 단위로 쪼갤까? 쪼개면 외움 표시 · 북마크 단위가 정확해지지만 기존 `flashcard_known_bogang119` 기록의 id 가 달라진다.
2. **기기 간 동기화**가 필요한가? (폰과 PC 를 번갈아 쓴다면 C 를 검토할 이유가 생긴다. 아니라면 P0 의 내보내기·가져오기로 충분하다.)
3. **일일 플랜(`day_checks`)과 로드맵(`roadmap_checks`)을 합칠까?** 합치면 Completion 이 한 체계가 된다.
